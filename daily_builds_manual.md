# 1. Project Overview

## 1.1 What Daily Builds is

Daily Builds is a GitHub-based automation that proposes a small, useful software project every morning, waits for explicit human approval, generates the approved project with LLM assistance, runs deterministic quality checks, opens a pull request, and then stops until a human reviews and merges it.

The intended lifecycle is:

```text
Idea
  v
Human chooses an idea
  v
Specification
  v
Tests
  v
Code
  v
Automated checks
  v
Pull request
  v
Human review
  v
Human merge
```

Nothing generated by the system should land on `main` without human review. The source plan defines the goals as one useful project per day, different technology stacks, two human approval points, one-command projects with tests and READMEs, and bounded cost/rate usage. 

## 1.2 Goals

The project must:

- produce one genuinely useful project per day;
- keep all projects in one GitHub monorepo;
- make each project solve a real problem;
- rotate technology stacks;
- require human approval before building;
- require human review before merging;
- give every project a README;
- give every project at least one meaningful test;
- run without paid external services;
- avoid duplicate ideas;
- keep model usage bounded.

## 1.3 Non-goals

Do not turn this into:

- a fully unattended publishing system;
- a general autonomous software company;
- a multi-service cloud platform;
- a database-backed SaaS application;
- a system that requires paid APIs to function.

## 1.4 Core mental model

Python owns deterministic orchestration.

LLMs make bounded decisions and generate bounded artifacts.

GitHub owns scheduling, issues, branches, pull requests, and audit history.

The human owns approval and merge.

This separation is important. If an LLM fails, Python should know how to stop. If a provider goes down, the router should know how to switch. If generated code is suspicious, the validation layer should stop the PR.

# 2. Plan Changes / Corrections

This section deliberately records corrections instead of silently changing the source plan.

## 2.1 PLAN CHANGE -- Fix attempt count

The source plan contains two different limits. One section says a maximum of two fix attempts; the detailed pipeline says three. The stricter value is used here:

**Maximum fixer attempts: 2.**

The flow is therefore:

```text
initial checks
    v fail
fix attempt 1
    v
checks
    v fail
fix attempt 2
    v
checks
    v fail
stop -- no PR
```

This also aligns with the cost-cap philosophy.

## 2.2 PLAN CHANGE -- CI permissions

The phone token and the Actions token have different purposes.

The phone token only needs:

```text
Actions: write
Issues: write
```

The build workflow itself needs enough permission to checkout/write generated content and create a PR. Use a narrow workflow permission block such as:

```yaml
permissions:
  contents: write
  issues: write
  pull-requests: write
```

Do not give the phone token contents write merely because CI needs it.

## 2.3 PLAN CHANGE -- cron timezone explanation

The plan specifies:

```text
0 4 * * *
```

and describes it as 08:00 UAE time. GitHub Actions cron is UTC, so 04:00 UTC corresponds to 08:00 in UAE.

## 2.4 PLAN CLARIFICATION -- `gh` authentication

The Actions runner can use the workflow-provided `GITHUB_TOKEN` through `GH_TOKEN`. There is no need to create a second long-lived personal token for CI PR creation.

## 2.5 VERIFY CURRENT DOCUMENTATION

Provider model IDs, free quotas, rate limits, API URLs, GitHub action versions, and API permissions can change. Values in `providers.json` marked `VERIFY_CURRENT_*` are placeholders, not claims that those values are permanent.

Before activation, check current official documentation and replace placeholders.

# 9. Git & GitHub Fundamentals

Git tracks versions. The normal lifecycle is:

```text
working tree
  v
git add
  v
staging
  v
git commit
  v
local history
  v
git push
  v
remote
```

Branches separate work:

```bash
git switch -c build/test-project
git add .
git commit -m "feat: test project"
git push -u origin build/test-project
```

The central safety model is:

```text
main = reviewed history
build/* = generated candidate
PR = review boundary
```

A token having permission to write does not mean the automation should write directly to `main`.

# 12. GitHub Issues and Events

The daily proposal issue is the human interface.

Example title:

```text
Ideas for 2026-10-07
```

The issue receives:

```text
approve 1
approve 2
approve 3
skip
```

## Why exact parsing matters

This is unsafe:

```python
if "approve" in body:
    build()
```

Because:

```text
I don't approve this
```

contains the word `approve`.

Use an exact pattern:

```text
^approve\s+[123]$
```

after trimming.

## Authorization

The workflow checks:

```text
comment.author.login == DAILY_BUILDS_APPROVER
```

and:

```text
issue has daily-ideas label
```

and:

```text
comment exactly matches approval grammar
```

All three are required.

# 13. GitHub REST API

HTTP consists of:

```text
method
URL
headers
body
```

Example comment request:

```text
POST /repos/OWNER/REPO/issues/123/comments
```

Headers:

```text
Authorization: Bearer TOKEN
Accept: application/vnd.github+json
X-GitHub-Api-Version: 2022-11-28
```

Body:

```json
{"body":"approve 2"}
```

A Python example:

```python
import os
import requests

response = requests.post(
    "https://api.github.com/repos/OWNER/REPO/issues/123/comments",
    headers={
        "Authorization": f"Bearer {os.environ['GITHUB_TOKEN']}",
        "Accept": "application/vnd.github+json",
        "X-GitHub-Api-Version": "2022-11-28",
    },
    json={"body": "approve 2"},
    timeout=30,
)
response.raise_for_status()
```

```text
401/403 authentication/authorization
404 resource or visibility problem
409 conflict
422 invalid request
429 rate limit
5xx server/provider failure
```

GitHub's current documentation maps fine-grained token permissions to individual REST endpoints, so permissions should be checked at endpoint level rather than guessed.

# 16. OpenAI-Compatible LLM APIs

## What it means

An OpenAI-compatible provider exposes an API with request conventions that resemble the OpenAI API. This allows the project to use one Python client abstraction for multiple providers.

Conceptually:

```text
Python SDK
    v
base_url
    v
provider
    v
model
```

The OpenAI Python client supports configurable endpoints. Provider-specific compatibility still has to be verified before use.

## Important values

### API key

Authentication credential.

### Base URL

Provider endpoint.

### Model ID

Exact model name accepted by the provider.

### Request

Usually includes:

```text
model
messages/input
output limits
```

### Response

Usually contains generated text.

## Minimal example

```python
from openai import OpenAI

client = OpenAI(
    api_key="example",
    base_url="https://provider.example/v1",
)

response = client.chat.completions.create(
    model="example-model",
    messages=[
        {"role": "user", "content": "Return JSON only: {\"ok\":true}"}
    ],
)

print(response.choices[0].message.content)
```

## Structured JSON

Never trust the model's claim that its output is valid JSON.

Do:

```text
model
 v
json.loads
 v
schema/required-key validation
 v
accept/retry/reject
```

The plan's fallback rule is one retry on the same model for malformed JSON, then switch models.

# 17. Provider Router

This is the most technically difficult subsystem.

The source design uses a provider pool with roles, tiers, least-recently-used selection, diversity, client-side throttling, cooldowns, and failure classification.

## 17.1 Selection flow

```text
Agent
  v
Router
  v
Role tier
  v
Eligible provider/model list
  v
Not cooling down
  v
Not excluded by diversity rule
  v
Quota available
  v
Least recently used
  v
API call
```

## 17.2 Provider configuration

Start with one provider:

```json
{
  "providers": [
    {
      "name": "github_models",
      "base_url": "VERIFY_CURRENT_ENDPOINT",
      "key_env": "GITHUB_TOKEN",
      "tier": "strong",
      "models": [
        {
          "id": "VERIFY_CURRENT_MODEL",
          "context_window": 32000,
          "rpm": 5,
          "rpd": 50
        }
      ]
    }
  ]
}
```

Do not treat these values as actual current quotas. Replace them only after checking current documentation.

## 17.3 Role tiers

Strong:

```text
planner
coder
moderator
```

Fast:

```text
skeptic
stack advocate
scope cutter
red team
fact checker
```

## 17.4 Failure behavior

```text
429 -> cooldown + next candidate
401/403 -> disable provider for run
5xx/timeout -> short cooldown + next
invalid JSON -> one same-model retry, then swap
context too long -> larger-context candidate
all strong models unavailable -> abort planner/moderator rather than silently use a weak tier
```

## 17.5 Router state

```python
from dataclasses import dataclass

@dataclass
class ModelState:
    provider: str
    model: str
    used_today: int = 0
    used_window: int = 0
    cooldown_until: float = 0.0
    last_used: float = 0.0
    exhausted: bool = False
```

## 17.6 Provider client

```python
from openai import OpenAI

client = OpenAI(
    api_key=os.environ[provider["key_env"]],
    base_url=provider.get("base_url"),
)
```

Only pass `base_url` when configured.

## 17.7 Diversity

If the planner used:

```text
provider/model-A
```

then the skeptic should receive:

```text
exclude_models={"provider/model-A"}
```

This does not guarantee intellectual diversity, but it prevents exact model duplication.

## 17.8 Call budget

Set:

```python
MAX_LLM_CALLS = 25
```

Increment the counter before or at each actual provider attempt, according to your chosen accounting rule. The rule must be documented and deterministic.

# 18. Rate Limiting and Token Buckets

A free model may impose both burst and average limits.

A token bucket models this well.

## Mental model

```text
capacity = 10 tokens
refill = 1 token/sec
```

A request consumes one token.

If the bucket is empty, wait.

## Implementation

```python
import time


class TokenBucket:
    def __init__(self, capacity: float, refill_per_second: float) -> None:
        self.capacity = capacity
        self.tokens = capacity
        self.refill_per_second = refill_per_second
        self.last = time.monotonic()

    def _refill(self) -> None:
        now = time.monotonic()
        elapsed = now - self.last
        self.tokens = min(
            self.capacity,
            self.tokens + elapsed * self.refill_per_second,
        )
        self.last = now

    def consume(self, amount: float = 1.0) -> bool:
        self._refill()
        if self.tokens < amount:
            return False
        self.tokens -= amount
        return True

    def wait(self, amount: float = 1.0) -> None:
        while not self.consume(amount):
            time.sleep(0.25)
```

## Why this does not replace provider headers

Client-side throttling is predictive. Provider responses are authoritative.

If the provider sends `Retry-After`, use it.

# 26. Security and Prompt Injection Protection

## 26.1 Issue comments are untrusted

The exact approval command must be accepted only from the configured user.

Unsafe:

```python
if "approve" in body:
    build()
```

Safe shape:

```python
APPROVE_RE = re.compile(r"^approve\s+([123])$", re.IGNORECASE)
```

Then verify the author.

## 26.2 Generated code is untrusted

Generated code can contain accidental or malicious behavior. Therefore:

- no provider secrets in generated project environment;
- no GitHub token in generated project environment;
- no trust in model-generated dependencies;
- no direct write to `main`;
- no unbounded network access where avoidable;
- no secret values in logs.

## 26.3 Secret scanning

At minimum inspect generated text for patterns:

```text
ghp_
github_pat_
-----BEGIN ... PRIVATE KEY-----
```

This is only a guardrail, not a replacement for dedicated secret scanning.

## 26.4 Shell injection

Do not interpolate issue comments directly into shell commands.

Bad:

```yaml
run: echo "${{ github.event.comment.body }}"
```

Instead pass data to a Python process through controlled environment variables or use event fields only after validation.

## 26.5 Permissions

Least privilege is a safety mechanism. Review every workflow permission whenever the workflow changes.

```python
import re


APPROVE_RE = re.compile(r"^approve\s+([123])$", re.IGNORECASE)


def parse_command(body: str) -> int | str | None:
```

## Checkpoint 4 -- Validation

### `scripts/validate.py`

```python
from __future__ import annotations

import re
from pathlib import Path


SECRET_PATTERNS = [
    re.compile(r"ghp_[A-Za-z0-9_]+"),
    re.compile(r"github_pat_[A-Za-z0-9_]+"),
    re.compile(r"-----BEGIN [A-Z ]+PRIVATE KEY-----"),
]


def count_lines(root: Path) -> int:
    total = 0
    for path in root.rglob("*"):
        if not path.is_file():
            continue
        if any(part in {".git", ".venv", "__pycache__"} for part in path.parts):
            continue
        try:
            text = path.read_text(encoding="utf-8")
        except UnicodeDecodeError:
            continue
        total += len(text.splitlines())
    return total


def scan_secrets(root: Path) -> list[str]:
    findings: list[str] = []
    for path in root.rglob("*"):
        if not path.is_file():
            continue
        if any(part in {".git", ".venv", "__pycache__"} for part in path.parts):
            continue
        try:
            text = path.read_text(encoding="utf-8")
        except UnicodeDecodeError:
            continue
        for pattern in SECRET_PATTERNS:
            if pattern.search(text):
                findings.append(str(path))
    return sorted(set(findings))


def validate_project(root: Path, max_lines: int = 200) -> list[str]:
    errors: list[str] = []

    if not (root / "README.md").exists():
        errors.append("README.md is missing")

    if not (root / "tests").exists():
        errors.append("tests directory is missing")

    if count_lines(root) > max_lines:
        errors.append(f"project exceeds {max_lines} lines")

    secret_files = scan_secrets(root)
    if secret_files:
        errors.append("possible secrets found: " + ", ".join(secret_files))

    return errors
```

### `scripts/github_api.py`

```python
from __future__ import annotations

import os
from typing import Any

import requests


class GitHubApiError(RuntimeError):
    pass


class GitHubClient:
    def __init__(self, token: str | None = None) -> None:
        self.token = token or os.environ["GITHUB_TOKEN"]
        self.base = "https://api.github.com"
        self.headers = {
            "Authorization": f"Bearer {self.token}",
            "Accept": "application/vnd.github+json",
            "X-GitHub-Api-Version": "2022-11-28",
        }

    def request(
        self,
        method: str,
        path: str,
        *,
        json: dict[str, Any] | None = None,
        params: dict[str, Any] | None = None,
    ) -> Any:
        response = requests.request(
            method,
            self.base + path,
            headers=self.headers,
            json=json,
            params=params,
            timeout=30,
        )
        if not response.ok:
            raise GitHubApiError(
                f"{method} {path} failed: {response.status_code} {response.text[:500]}"
            )
        if not response.content:
            return None
        return response.json()

    def list_open_daily_ideas(self, owner: str, repo: str) -> list[dict[str, Any]]:
        return self.request(
            "GET",
            f"/repos/{owner}/{repo}/issues",
            params={"labels": "daily-ideas", "state": "open", "per_page": 10},
        )

    def comment(self, owner: str, repo: str, issue: int, body: str) -> Any:
        return self.request(
            "POST",
            f"/repos/{owner}/{repo}/issues/{issue}/comments",
            json={"body": body},
        )
```

## 33.2 Router implementation

The router should expose one method to the rest of the system:

```python

    role="planner",
    tier="strong",
    messages=messages,
)
```

The rest of the code must not know whether the provider is Gemini, Groq, GitHub Models, Mistral, OpenRouter, NVIDIA, or another configured service.

### Router invariants

1. No provider key means provider is skipped.
2. A 429 puts the model into cooldown.
3. A 401/403 disables that provider for the run.
4. A 5xx causes a short cooldown.
5. Invalid JSON gets one retry, then another model.
6. A critic cannot use the exact model it critiques.
7. The global call budget cannot be exceeded.
8. Planner/moderator should not silently downgrade to a weak tier when the strong tier is unavailable.

## 33.4 Debate runner

5. run at most two rounds;

```python
def debate(stage, context):

    decision = moderate(round_one)

    if decision_requires_revision(decision):
        round_two = run_agents(stage, merge(context, decision))
        decision = moderate(round_two)

    write_debate(stage, ...)
    return decision
```

# Deep Reference 1 -- `propose.yml`

The proposal workflow should have two entry points: the scheduled event and manual dispatch.

A practical baseline is:

```yaml
name: Daily Ideas

on:
  schedule:
    - cron: "0 4 * * *"
  workflow_dispatch:

permissions:
  contents: read
  issues: write

jobs:
  propose:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - name: Install dependencies
        run: python -m pip install -r requirements-dev.txt

      - name: Generate ideas
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          GITHUB_OWNER: ${{ github.repository_owner }}
          GITHUB_REPO: ${{ github.event.repository.name }}
          DAILY_BUILDS_APPROVER: ${{ vars.DAILY_BUILDS_APPROVER }}
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
          GROQ_API_KEY: ${{ secrets.GROQ_API_KEY }}
          CEREBRAS_API_KEY: ${{ secrets.CEREBRAS_API_KEY }}
          MISTRAL_API_KEY: ${{ secrets.MISTRAL_API_KEY }}
          OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
          NVIDIA_API_KEY: ${{ secrets.NVIDIA_API_KEY }}
        run: python -m scripts.propose

      - name: Upload logs
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: proposal-logs
          path: build_logs/
          if-no-files-found: ignore
```

## Why each part exists

### `schedule`

This creates the morning proposal.

### `workflow_dispatch`

This makes debugging and phone shortcuts possible.

### `permissions`

Proposal generation should not need repository contents write or pull-request write. Keeping the proposal job read-only for contents limits damage.

### `timeout-minutes`

A provider outage should not leave a runner waiting indefinitely.

### `actions/checkout`

The script needs `ideas.json`, `stacks.json`, `providers.json`, and agent prompts.

### `setup-python`

The runner should use the same Python major/minor version as local development.

### pip cache

This reduces installation time without becoming a correctness dependency.

### environment variables

Secrets are injected only into the step that needs them.

### artifact upload

Even failed proposals should leave enough evidence to diagnose the problem.

# Deep Reference 2 -- `build.yml`

The build workflow has two triggers:

```yaml
on:
  issue_comment:
    types: [created]
  workflow_dispatch:
    inputs:
      issue_number:
        description: "Daily ideas issue number"
        required: true
        type: string
      idea_number:
        description: "Idea number 1-3"
        required: true
        type: string
```

A practical permission block is:

```yaml
permissions:
  contents: write
  issues: write
  pull-requests: write
```

The first job should not immediately run the generator. It should validate the trigger.

Conceptually:

```text
trigger
 v
if issue_comment:
    check issue
    check label
    check author
    parse exact command
if workflow_dispatch:
    validate issue_number
    validate idea_number
 v
only then
 v
build.py
```

## Why validation must happen before checkout-driven generation

An attacker should not be able to spend your model quota simply by commenting on an arbitrary issue.

The authorization boundary comes before expensive work.

## `issue_comment` event payload

The event contains a comment object and an issue object. Do not assume the event is always an ordinary issue. A comment can also be associated with a pull request because GitHub models pull requests as issues with additional fields.

The build should therefore explicitly require:

```text
issue is a normal daily-ideas issue
```

and should reject unrelated PR comments.

This matters because GitHub events can be retried, workflows can be manually rerun, and humans can post duplicate comments.

# Deep Reference 6 -- Stack Rotation Algorithm

The stack rotation rule is a constraint, not merely a suggestion.

## Input

```text
ideas.json
stacks.json
```

## Algorithm

```python
def recently_used(projects: list[dict], n: int = 7) -> set[str]:
    return {item["stack"] for item in projects[-n:]}
```

Then:

```python
blocked = recently_used(history)
allowed = [stack for stack in stacks if stack["name"] not in blocked]
```

The planner receives only `allowed` stacks.

This is stronger than asking the model to remember the rule.

## Why enforce it in code

A prompt is not a constraint. It is an instruction to a probabilistic model.

A Python validation function is deterministic.

Therefore:

```text
prompt says stack must differ
+
Python checks stack differs
```

is safer than prompt-only enforcement.

# Deep Reference 7 -- Problem Deduplication

Start with deterministic normalization.

```python
import re


def normalize_problem(value: str) -> str:
    value = value.lower()
    value = re.sub(r"[^a-z0-9\s]", " ", value)
    return " ".join(value.split())
```

Then compare:

```python
new = normalize_problem(candidate["problem"])

for old in history:
    if new == normalize_problem(old["problem"]):
        reject()
```

Only add semantic similarity later.

## Why not embeddings first?

Because the system itself is supposed to remain small. Adding a vector database or embedding provider to prevent duplicate one-sentence ideas creates a larger system than the problem requires.

# Deep Reference 8 -- Project Slugs

A slug is used for both the directory and branch.

Example title:

```text
CSV Duplicate Finder
```

Slug:

```text
csv-duplicate-finder
```

A safe slug function:

```python
import re


def slugify(title: str) -> str:
    value = title.lower()
    value = re.sub(r"[^a-z0-9]+", "-", value)
    value = value.strip("-")
    return value[:60]
```

If the result is empty, reject the idea rather than inventing a random name.

Starts the project with one command.

## Why this abstraction matters

The build pipeline can do:

```python
run(stack["install"])
run(stack["test"])
run(stack["lint"])
```

without knowing whether the project is Python, Go, Rust, Bash, or TypeScript.

## Security warning

Do not execute stack commands obtained from the LLM. They must come from the committed `stacks.json` allowlist.

The model chooses a stack name; the repository configuration supplies the command.

This is a critical trust boundary.

---

# Deep Reference 11 -- Safe Subprocess Execution

The project runs commands on generated code, so subprocess handling matters.

Prefer:

```python
subprocess.run(
    ["python", "-m", "pytest"],
    cwd=project_dir,
    capture_output=True,
    text=True,
    timeout=120,
    check=False,
)
```

Avoid:

```python
subprocess.run(user_supplied_string, shell=True)
```

For stack commands stored as strings, either use a controlled command representation or a tightly constrained parser. Do not let a generated project rewrite `stacks.json` and then execute the rewritten command.

## Timeout

Every external process must have a timeout.

A test suite that hangs should become:

```text
timeout
```

not an infinite Actions job.

# Deep Reference 12 -- Build Workspace Isolation

Each build should have a temporary workspace before moving accepted output into the final project path.

Conceptually:

```text
projects/<final>

      ^ only after validation

/tmp/daily-build/<run-id>
```

Why?

If generation fails halfway through, the repository should not contain a half-generated project that looks complete.

## Safer sequence

```text
create temp workspace
 v
generate files
 v
test
 v
lint
 v
secret scan
 v
README validation
 v
review
 v
copy/move to final project path
```

This also makes cleanup easier.

# Deep Reference 13 -- File Write Safety

Generated file paths are model-controlled data. Do not allow a model to request:

```text
../../.github/workflows/build.yml
```

or:

```text
../../.env
```

## Safe path rule

The requested path must remain inside the generated project root.

Conceptually:

```python
candidate = (root / relative_path).resolve()
root_resolved = root.resolve()

if root_resolved not in candidate.parents and candidate != root_resolved:
    raise ValueError("path escapes project root")
```

This is essential because file generation is an input-validation boundary.

# Deep Reference 14 -- README Verification

The README writer is not trusted simply because it is an LLM.

After it writes the README, verify required headings:

```python
required = [
    "## Problem",
    "## Solution",
    "## Why this stack",
    "## Usage",
    "## Tests",
]
```

Then:

```python
text = readme.read_text(encoding="utf-8")
missing = [heading for heading in required if heading not in text]
```

If anything is missing:

```text
fact-checker/writer revision
```

not an immediate PR.

# Deep Reference 15 -- Problem-First Review

The reviewer should answer four questions:

1. What problem was promised?
2. What user has that problem?
3. What behavior solves it?
4. Can the acceptance test demonstrate that behavior?

If the code is impressive but does not answer those four questions, reject it.

This protects the project from drifting into:

```text
interesting demo
```

instead of:

```text
useful tool
```

# Deep Reference 16 -- Why Stack Review

The README must explain:

```text
Why this stack?
What alternative was considered?
Why was it rejected?
What trade-off does the chosen stack make?
```

Bad:

```text
Python was chosen because Python is easy.
```

Better:

```text
Python was chosen because the problem is local CSV transformation and the standard library provides the required file-processing primitives with very little setup. TypeScript was considered but rejected because the project does not need a browser/runtime ecosystem.
```

The point is not to prove that Python is universally better. It is to demonstrate deliberate selection.

# Deep Reference 17 -- Provider Router Test Matrix

The router should have tests for every branch of the failure table.

| Scenario | Expected action |
|---|---|
| provider has no key | skip |
| model cooling down | skip |
| model daily quota exhausted | skip |
| model minute quota exhausted | skip/wait |
| success | return |
| 429 | cooldown and next |
| Retry-After | honor it |
| 401 | disable for run |
| 403 | disable for run |
| 500 | short cooldown |
| timeout | short cooldown |
| invalid JSON | retry once |
| second invalid JSON | swap |
| context too long | larger-context candidate |
| all models unavailable | controlled failure |
| call budget exhausted | controlled failure |

This table should become actual unit tests.

# Deep Reference 18 -- Provider Router Logs

Every router call should emit a structured event.

Example:

```json
{

  "role": "planner",
  "provider": "gemini",
  "model": "verified-model",

  "result": "success",
```

On failure:


# Deep Reference 19 -- Model Diversity Implementation

Diversity should be deterministic.

Suppose:

```text
planner -> provider-A/model-X
```

Then:

```text
skeptic excluded_models = {provider-A/model-X}
```

The router can still choose:

```text
provider-B/model-Y
provider-C/model-Z
```

If no different model is available, the router should fail the diversity requirement explicitly rather than pretending diversity occurred.

A future configuration option can allow the human to override this behavior, but the default should follow the plan.

# Deep Reference 20 -- Debate State Machine

The debate runner is easier to reason about as a state machine.

```text
START
  v
DRAFT
  v
CRITIQUE_ROUND_1
  v
MODERATE
  |---- ACCEPT -> FINAL
  |---- REJECT -> STOP
  `---- REVISE
          v
    CRITIQUE_ROUND_2
          v
       MODERATE
          v
        FINAL
```

There must be no transition from `CRITIQUE_ROUND_2` back to `CRITIQUE_ROUND_1`.

That would violate the bounded-round rule.

# Deep Reference 24 -- Index Update

The index updater should derive the README table from project history rather than relying on an LLM.

Example table:

```markdown
| Date | Project | Problem | Stack | PR |
|---|---|---|---|---|
| 2026-10-07 | CSV Duplicate Finder | Find duplicate CSV rows | Python | #12 |
```

## Why deterministic indexing

There is no reason to spend an LLM call to generate a table from structured data.

Use Python.

This is an important architectural principle:

> Use an LLM only where interpretation or generation is actually needed.

# Deep Reference 25 -- `update_index.py` Strategy

The index updater should:

1. find merged project records;
2. sort by date descending;
3. generate a stable Markdown table;
4. replace only a marked region in README;
5. write the file;
6. commit if the file changed.

Use markers:

```markdown
<!-- DAILY_BUILDS_INDEX_START -->
...
<!-- DAILY_BUILDS_INDEX_END -->
```

Do not ask the LLM to rewrite the entire README.

This makes the update idempotent.

# Deep Reference 26 -- `ideas.json` Update Strategy

Only a merged project should be recorded as completed.

The record should contain enough history to enforce:

```text
problem deduplication
stack rotation
```

Example:

```json
{
  "date": "2026-10-07",
  "title": "CSV Duplicate Finder",
  "problem": "People need to identify duplicate rows in CSV exports.",
  "stack": "python",
  "slug": "csv-duplicate-finder",
  "status": "merged",
  "pr": 12
}
```

Do not append an idea to completed history when its build fails and no PR is merged.

You may separately retain rejected/failed proposal metadata in a future history field, but the rotation list should use completed projects.

# Deep Reference 27 -- `index.yml` Safety

A README-index workflow can accidentally trigger itself.

Example dangerous cycle:

```text
push
 v
index workflow
 v
commit README
 v
push
 v
index workflow
 v
...
```

Prevent this by making the updater commit recognizable and excluding it from its own trigger logic, or by triggering from a merge-specific event that does not respond to its own bot-generated commit.

Always test this in a branch before enabling it on `main`.

# Deep Reference 28 -- Repository Branch Protection

The plan's safety model is stronger when the GitHub repository itself also protects `main`.

Recommended policy:

```text

Restrict direct pushes where practical
```

The automation should therefore have no legitimate reason to push directly to `main`.

Even if a workflow is accidentally modified later, repository protection provides another independent barrier.

# Deep Reference 30 -- Dependency Pinning

The plan requires pinned dependencies for generated projects.

There are several meanings of "pinned":

```text

bounded version
lock file
```

For the generated projects, prefer a lockfile or exact versions where the ecosystem makes this practical.

For Daily Builds itself, bounded versions in `requirements.txt` can be combined with a controlled upgrade process.

Do not automatically upgrade all dependencies on every build. Dependency updates are a separate maintenance activity.

# Deep Reference 34 -- Human Approval Points

# Deep Reference 39 -- Incident Recovery

If a generated PR contains dangerous code:

1. Do not merge.
2. Close the PR.
3. Delete the generated branch if appropriate.
4. Inspect the logs.
5. Determine whether any secret was exposed.
6. Rotate affected secrets immediately if exposure is possible.
7. Fix the guardrail.
8. Re-run the test that should have caught it.
9. Only then resume Daily Builds.

If a phone token is exposed:

1. revoke it;
2. create a new token;
3. verify shortcut storage;
4. test the least-privilege permissions;
5. document the incident.

# Deep Reference 41 -- Provider Removal Procedure

If a provider becomes unreliable:

1. remove or disable it in `providers.json`;
2. do not delete historical logs;
3. keep the router capable of skipping it;
4. run tests;
5. verify another provider works;
6. update Project State.

The architecture should make provider replacement a configuration change whenever possible.

# Deep Reference 48 -- What to Do If You Get Stuck

Use this decision tree.

```text

     v

     |---- yes -> reproduce
     `---- no -> inspect Actions logs
                 v

     |---- GitHub event -> workflow/event
     |---- auth -> permissions/token
     |---- router -> provider config
     |---- generation -> prompt/model
     |---- tests -> generated project
     |---- lint -> generated source
     |---- PR -> git/gh/permissions

                 v

                 v

                 v

```

Do not make unrelated changes while diagnosing a failure.

# Deep Reference 50 -- Long-Term Operating Principle

The system should become better through evidence, not through increasing complexity.

If five projects fail because the planner creates overly large scopes, improve the planner prompt and scope validation.

Do not immediately add another framework.

If provider A repeatedly hits limits, adjust routing.

Do not immediately add a database.

If generated projects repeatedly expose secrets, strengthen the sandbox and scanner.

Do not simply tell the model to "be careful."

The design philosophy is:

```text
observe failure
 v
identify violated invariant
 v
add deterministic guardrail where possible
 v
add a regression test
 v
continue
```

That is how Daily Builds becomes reliable without becoming unnecessarily large.
